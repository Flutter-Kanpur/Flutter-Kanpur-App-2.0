Persistent project memory. Read at the start of every session; append (never overwrite) at the end of every task/milestone.

## Project Overview

`flutter_knp_mobile_app_v2` — the Flutter Kanpur community app. Feature-first module layout under `lib/modules/` (`auth`, `blogs`, `community`, `contributor`, `events`, `explore`, `home`, `legal`, `onboarding`, `profile`, `support`), each typically split into `data/` (repositories/data sources), `domain/` (models), `application/` (Riverpod providers), `presentation/` (`screens/`, `widgets/`). Shared cross-module pieces live in `lib/shared/` (widgets), `lib/app/` (router, theme), `lib/core/` (database tables/constants), `lib/utils/` (asset paths, helpers).

## Key Architecture Decisions

- **State management**: `flutter_riverpod` (v3), exclusively - `StatefulWidget`/`setState` is not used anywhere in this app, including tiny widget-local state (a like-heart, a toggle). Synchronous local/sample data uses plain `Provider`; real or simulated-async fetches use `AsyncNotifierProvider<Notifier, T>` consumed via `.when(loading/error/data)` in `ConsumerWidget`s. `communityProjectsProvider` (`lib/modules/community/application/community_provider.dart`) is the reference implementation this pattern is copied from throughout.
- **Backend**: Supabase (`supabase_flutter`). Repositories take an optional `SupabaseClient` in their constructor (defaulting to `Supabase.instance.client`) so they're swappable in tests. Table names are centralized in `lib/core/database/database_tables.dart` (`DatabaseTables`) — never hardcode a table string.
- **Routing**: `go_router` with `StatefulShellRoute.indexedStack`. Screens reachable by push but not shown in the bottom nav (e.g. `ManageProfile`, `MyEvents`) are still registered as hidden shell branches so their navigation stack persists.
- **Design tokens**: `AppColors`, `AppTextStyles` (font: ProductSans), `AppSpacing` (`.h`/`.v` values scaled via ScreenUtil `.r`), `AppRadius`, `AppBorders` — always reuse these instead of hardcoding colors/spacing/fonts.
- **Assets**: generic, purpose-named files live in the shared `assets/icons/` folder (registered once in `pubspec.yaml`) and are exposed via `lib/utils/assets_path.dart` (`AssetsPath`) or `lib/core/constants/app_assets.dart` (`AppAssets`) — two separate constant classes exist historically; check both before adding a new asset path.
- **Skeleton loading**: composed from shared `FkSkeletonBlock` (single rectangle placeholder) + `FkSkeletonPulse` (opacity-pulse wrapper) in `lib/shared/widgets/` — do not hand-roll a new `AnimationController` per skeleton widget.
- **Avatar fallback convention**: two competing patterns exist — initials-in-a-CircleAvatar (`CommunityAvatar` in `community_author_row.dart`, used for questions/answers) vs. a literal default-avatar SVG asset (`AppAssets.avatarIcon`, used in onboarding and now Explore's Core Team). Pick whichever the calling context already favors; don't introduce a third pattern.

## Known Tech Debt

- `lib/app/router/navigation_provider.dart` has a `const bool bypassAuthForTesting = true;` flag that short-circuits the real auth-check logic in `nextRouteProvider`. This is local dev/testing scaffolding — **must be set back to `false` (or removed) before any release build**. Flagged repeatedly; not yet resolved.
- Two duplicate asset-path constant classes (`AssetsPath` and `AppAssets`) with overlapping purposes — should eventually be merged, but out of scope for incremental feature work.
- Explore dashboard (`lib/modules/explore/`) is a hybrid: Core Team is now real Supabase data (`ExploreRepository`); Hero banner, Community Projects preview, and Suggested Jobs preview are still sample data served through `ExploreLocalDataSource` (deliberately shaped like a repository so each can be swapped to a real backend independently, one section at a time).

### 2026-08-19 — Projects list: real search (typed + voice + filter chips)

**Why**: The search bar and filter chips on the Projects list had been decorative since the Figma rebuild. Requirement: search must hit the database (`ilike`), not just filter whatever's already loaded; typing should still feel instant via a frontend pre-filter while a debounced backend request confirms it; a filter chip (e.g. "UI/UX", "DSA") just fills the search box and searches on that, nothing chip-specific; skeleton cards while a search is actually in flight (`iPhone 16 - 310.svg`); a dedicated "No results found" state (`iPhone 16 - 307.svg`); and voice input on the mic icon.

**What changed**:
- `lib/modules/explore/data/repositories/explore_repository.dart` — `searchProjects(query, {limit = 20})`: same select/join shape as `fetchLatestCommunityProjects`, but `.ilike('title', '%$query%')` instead of just newest-first. Title-only search, matching what the card actually displays.
- `lib/modules/explore/application/explore_providers.dart` — `ProjectSearchState`/`ProjectSearchNotifier`/`projectSearchProvider`, a plain `Notifier` (not `AsyncNotifier`) so loading is controlled by hand rather than via `AsyncValue` transitions - this codebase's first debounced-search provider (no prior `Timer`-based pattern existed to copy; Home's own search is local-filter-only, no backend hit). `setQuery()` (every keystroke): instantly narrows whatever `communityProjectsPagedProvider` already has loaded (frontend-only, just to avoid a blank screen while typing), then debounces 400ms before firing the real `ilike` request, tracked via an incrementing `_requestId` so a stale in-flight response can't clobber a newer one. `submit()` (chip tap / keyboard submit) skips the debounce and searches immediately. `isSearching` is only true once the debounced request has actually been sent - that's what gates the skeleton state, not the local pre-filter.
- `lib/common_widgets/search_bar.dart` — `CommonSearchBar` gained an `isListening` param (default `false`, purely visual): swaps the mic icon to filled/`primary500` while a caller's speech session is active. Doesn't own any listening state itself.
- `lib/modules/community/presentation/screens/community_projects_screen.dart` — converted `ConsumerWidget` → `ConsumerStatefulWidget` (needed a `TextEditingController` + `SpeechToText` instance to own/dispose). Search-active (`projectSearchProvider.isActive`) fully replaces the paginated list below the search bar/chips - the "Load more"/"View less" pagination UI only applies to the non-search view; search results are a flat top-`limit` list with no pagination of their own (not requested). Filter chips (`_FilterChipsRow`) now show a real selected state (blue border + "✕", same convention `HomeFilterTabs` already uses for its own selection UI) driven by whether the current search query case-insensitively matches a chip's label; tapping a chip calls `submit()` with its label, tapping the already-selected one clears the search. `_NoSearchResultsView` reuses the exact copy the Figma shows (same as the general "no projects at all" empty state - the Figma didn't write search-specific copy either).
- **New dependency**: `speech_to_text: ^7.3.0` (resolved to 7.4.0), for the mic icon. `SpeechToText.initialize()` + `.listen(listenOptions: SpeechListenOptions(listenMode: ListenMode.search, partialResults: true, ...))`; each partial/final result is written into the search controller and immediately re-runs `setQuery()`. **Native permissions added** (per the package's own README): Android `RECORD_AUDIO`/`BLUETOOTH`/`BLUETOOTH_ADMIN`/`BLUETOOTH_CONNECT` permissions plus a `<queries>` entry for `android.speech.RecognitionService` (required on SDK 30+) in `android/app/src/main/AndroidManifest.xml`; iOS `NSMicrophoneUsageDescription`/`NSSpeechRecognitionUsageDescription` in `ios/Runner/Info.plist`. **Not verified end-to-end** - no physical device/mic available in this environment; only that it compiles and the listening-state UI toggles. A full rebuild (not just hot reload/restart) is needed on-device to pick up the new native plugin.

**Note**: search matches on `title` only (not summary/description/tech stack) - if broader matching is wanted later, that's a `.or('title.ilike.%$query%,summary.ilike.%$query%')`-style change to `searchProjects` alone, nothing else touches the query.

### 2026-08-19 — Community Projects narrowed to owned/shared only

**Why**: "Community Projects" (the list, its search, and the Explore dashboard preview) had been a public browse of every `status = 'active'` project. Changed to a personal scope: only projects the signed-in user owns (`owner_uid`) or that have been shared with them (an active `project_members` row) are fetched at all now - not a UI-level filter, the query itself no longer returns other users' projects.

**What changed**:
- `lib/modules/explore/data/repositories/explore_repository.dart` - new private `_visibleProjectIds()`: two lightweight id-only queries (`projects` where `owner_uid = currentUserId`, and `project_members.project_id` where `user_uid = currentUserId AND active = true`), unioned into one `Set<String>`. Chose two small queries + an `id IN (...)` filter on the real data query over trying to `OR` across a joined table in one PostgREST call - simpler to write and to reason about, and this reuses the exact membership concept `_fetchSharedOn` (added for the detail screen's "Shared on" line) already established.
- Both `fetchLatestCommunityProjects` and `searchProjects` now call `_visibleProjectIds()` first and add `.inFilter('id', ids)` to their query, short-circuiting to `[]` if the set is empty (a user with nothing owned or shared sees nothing, not an error). The existing `status = 'active'` filter was kept as an *additional* condition, not replaced - a reasonable default since removing it wasn't explicitly requested, but worth confirming: it currently means even a user's own `draft`/`pending_review` projects won't show in their own list.
- `fetchProjectById` (the detail screen) was **not** touched - this change only scopes the list/search fetches, not direct-by-id access. RLS still permits any authenticated user to read any non-deleted project by id regardless of ownership, so a project not owned/shared could still be opened via a direct link if one existed; nothing currently constructs such a link outside this now-scoped list, but that's a gap if deep-linking to arbitrary ids becomes a real path.

### 2026-08-20 — Contest cards: live per-second countdown

**Why**: "each card will run the timer till the endDate time... each second decrease till 0000 and also dispose that timer when its not visible for optimization." `ContestPreview.metaValue` already recomputed the countdown string from `DateTime.now()` on every rebuild, but nothing was triggering a rebuild every second - the countdown only advanced whenever some other rebuild happened to fire.

**What changed**: `lib/modules/explore/application/contest_providers.dart` - new `contestCountdownTickerProvider`, a `StreamProvider.autoDispose<int>` ticking every second, same pattern as `contestsTickerProvider` in `lib/modules/profile/application/my_contests_provider.dart` (not shared/imported across modules - duplicating a 3-line ticker was simpler than coupling the two modules for it). `.autoDispose` cancels the underlying `Stream.periodic` once no card is watching it (i.e. once the Contests screen is left - the list isn't lazily built, so all cards mount/unmount together with the screen, not per-scroll-visibility).
